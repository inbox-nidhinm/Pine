# Pine: notes for working on it

Pine is a menu bar colour picker (no Dock icon, `LSUIElement`): a global shortcut (⇧⌘C by default, a Carbon hotkey, so no Accessibility permission) picks a colour from the screen with `NSColorSampler` and copies its hex code; the menu bar keeps the last five; a Compare window shows two colours with their WCAG contrast; a Settings window holds the shortcut, hex format and launch at login. Launching it again while it runs opens Compare. Bundle id `com.nidhin.pine`; the GitHub repo is `inbox-nidhinm/Pine` (private).

It was called Niram until 10 October 2026, when the user asked for Pine everywhere: the folder, the package, target and sources, the bundle id, the repo, the logs folder and every word in the app and its history. `App/FormerName.swift` is the only code with the old name: on the first launch as Pine it copies the `com.nidhin.niram` settings domain across when Pine has none, and moves `~/Library/Logs/Niram` to `Pine` when there is none (once, never in the test copy).

It is being redesigned the way Flip and Twine were made: `docs/redesign-decisions.md` holds the user's answers. The steps, each ending with screenshots for the user to check before the next: 1 foundations (done), 2 the menu bar dropdown as a custom floating panel (done), 3 the Compare window (done), 4 Settings as cards, as Twine's Settings page (done), 5 an app icon (needs the user's artwork).

## Rules

These follow Twine's (`../Twine/CLAUDE.md`), which has the reasons.

- **No em dashes anywhere**: UI strings, comments, docs, commit messages.
- No third-party dependencies without asking.
- Every milestone ends with: `./make-app.sh` with no warnings, `./test.sh` passing, the change written into the top build of `Sources/Pine/App/VersionHistory.swift`, a commit, a push to `inbox-nidhinm/Pine`, and then `./install.sh` (outside the command sandbox), which quits the running Pine, replaces `/Applications/Pine.app` whole and starts the new build (the user's request, 6 October 2026: every update is installed and launched at once). Build after the commit's last edit, so what is installed is what was pushed.
- **Builds are releases, not changes**: write each change as a line in the top build's `features`, `fixes` or `misc`; start a new build only when the user says to cut one. Raise `VersionHistory.pushes` by one in every commit you push.
- The user is a designer, not an engineer. Explain in plain terms.
- No help text in the UI, and no tooltips either (the user had every hover hint removed on 6 October 2026, so never add `.help()` or `toolTip`). States are shown, not explained.
- Views never write literals: every colour, size and radius comes from `Theme` (`Sources/Pine/Theme/Theme.swift`), the Flip Design System's values as Twine has them, with magenta (#E2387F) as the accent. The surface, text, edge, chosen and switch colours are adaptive (`Theme.adaptive(dark:light:)`): each draws by the appearance of its window. Settings and the Compare card take `AppSettings.appearance.window`; the menu bar panel is always dark; the card's own colours (`middle...`, `textOnLight`/`textOnDark`) are fixed, so never borrow an adaptive token for something read against a picked colour.
- **Never drive the copy of the app the user is using** (`/Applications/Pine.app`, usually running); the one exception is `./install.sh` replacing and restarting it at the end of a change. For checks, copy `build/Pine.app` to the scratchpad, give the copy the bundle id `com.nidhin.pine.selftest` (`plutil -replace CFBundleIdentifier`, then `codesign --force --sign - --options runtime`), and run its binary directly. Its shortcut will not register while the user's copy holds it. To open a window without clicking, add a temporary environment-variable hook in `AppDelegate.applicationDidFinishLaunching`, between a `// TEMPORARY TEST HOOK` line and an `// END TEST HOOK` line, and remove it with `python3 Tools/remove-hook.py` (which refuses unless both markers are there once) before committing; chain the final build, test, commit, push and install with `&&` only, so nothing is committed or installed after a failed build (on 6 October 2026 a hook cut at the wrong line was pushed broken); capture windows with `screencapture -o -l<window id>`, the id from `CGWindowListCopyWindowInfo` for the copy's pid, of any layer (the menu bar panel is at the pop-up menu level, 101; a menu bar app also has a small window of its own). Clicks: post `NSEvent` mouse events through the window's `sendEvent` from the hook, then an `.applicationDefined` event through `NSApp.postEvent`, and log with `NSLog` (a `print` is lost when the copy is killed). A posted click into a SwiftUI text field does focus it (the field editor becomes first responder), and posted key events type into it. Never click a recent colour in a test: it copies to the user's real clipboard. Give the test copy sample colours with `defaults write com.nidhin.pine.selftest recentColors -array ...` and delete that domain afterwards. The user's menu bar is full: a second Pine icon goes behind the notch, and its panel then opens mid-screen.

## Building

SwiftPM, no Xcode project. `./install.sh` installs and starts `build/Pine.app` (see Rules). `./make-app.sh` builds release (or `debug`), assembles `build/Pine.app` from the binary and `Resources/` (Info.plist, PP Kyoto in `Fonts`, the grain in `Textures`), writes the version (the count of builds in `VersionHistory`) and signs it ad hoc with the Hardened Runtime. Resources are copied in by the script rather than declared in `Package.swift`, because SwiftPM's resource bundle sits at the app's root, where signing refuses it; code finds them with `Bundle.main` (under `swift run` the fonts fall back to the system face and there is no grain). `./test.sh` runs the unit tests in `Tests/PineTests` (Swift Testing, `@testable import Pine`). macOS 14 or later.

## Picking

The eyedropper is macOS's, not Pine's: `NSColorSampler` asks the ColorSampler service (`/System/Library/Frameworks/AppKit.framework/Versions/C/XPCServices/ColorSampler.xpc`), its own process, to put a window over every screen connected at that moment, at level 2147483631, plus a 153-point magnifier that follows the pointer. It cannot be cancelled through the API, it outlives its client, and it ignores a polite quit (`SIGKILL` ends it; macOS starts it again when next asked). Twice on 6 October 2026 the user's screens took no clicks at all, the Dock and menu bar included, with no way out but forcing the Mac off; the second time the shortcut did not help either, so nothing may rely on the user reaching Pine.

- `ColorPicking` (main actor): one pick at a time, the sampler held until it answers. A new pick waits (`prepare`) for the screen to be clear of any eyedropper; one still up after `fadeWait` (1 s) is ended, then it waits for the service to be gone and `restartPause` before asking. Asking at once after ending the service (the first fix did) gave a pick that never appeared and never answered, and a killed service can show a pick seconds late. `toggle` (the shortcut) ends a pick under way; quitting ends one.
- `SamplerWatchdog` (its own queue, every 0.5 s, started first thing at launch) reads `PickState` (a lock, not the main actor) and `SamplerService.snapshot()` and ends the service when the screen is covered with no magnifier for 1.5 s (the stuck state: plain pointer, hover working, no click landing), when covers outstay Pine's pick by 2 s (within 60 s of it; later ones are taken to be another app's), or when a pick passes 2 minutes; and lets go of a pick with nothing on screen for 1.5 s. It does not need the main thread: with the main thread frozen for 5 s it ended a stuck eyedropper at 2.5 s.
- `SamplerService`: the snapshot (covers and magnifiers by window owner and size, no screen recording permission needed) and `end(because:)`. `EyedropperLog` writes every ending and let-go to `~/Library/Logs/Pine/eyedropper.log`: read it first when the user reports a stuck screen.
- A covered screen with no magnifier has not been reproduced on purpose; the rule for it is from the user's description. A completed pick needs a real click.

**Testing a pick takes over the user's real pointer and screen**, and the user may be clicking (a test pick was once completed by their click): warn them first, keep every run under a hard limit (`perl -e 'alarm 15; exec @ARGV' ...`), leave three seconds between runs (a pick asked just after the service was ended never shows), and check the screen afterwards with a window list, ending the service by hand if anything is left. Run the test copy outside the command sandbox, which blocks the signal.

## Icons

The app icon is the designer's artwork, `Artwork/AppIcon.png` (a full-bleed square, from `~/Desktop/06-10/Icon2.png`, the yellow one, which replaced `Icon.png` on 7 October 2026), set into the macOS icon grid by `swift Tools/make-app-icon.swift Artwork/AppIcon.png Resources/AppIcon.icns` (Twine's tool). The menu bar icon is the designer's `Resources/menu-icon.svg`, drawn by macOS from the SVG as a template image. `make-app.sh` copies both into the app.


SVGs in `Icons/`, 24x24, stroked, `M L H V C Z` only, drawn at `Theme.iconStroke`. All but `copy.svg` are the designer's, copied from Twine's set; `copy.svg` is a placeholder of ours. Regenerate after editing:

```bash
python3 Tools/svg_to_swift.py --icons Icons --out Sources/Pine/Theme/Icons.swift
```
